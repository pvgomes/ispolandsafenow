# Scheduler

A small, separate Cloudflare Worker (its own `wrangler.jsonc`, deployed
independently from the main site Worker) that classifies all 16 regions
once per hour and writes the result to D1. The main site never calls
TypeSafe AI itself — every page and API response is a plain D1 read
(`RegionRepository`) — so traffic to the site has no effect on AI usage
or cost, whether that's 10 visitors an hour or 10,000.

## Why a second Worker

The main Astro Worker's entrypoint is fully generated by
`@astrojs/cloudflare` (see `ARCHITECTURE.md`'s note on the build model) —
there's no place in that generated output to hang a custom `scheduled()`
export. A second, plain Worker with its own Cron Trigger is the
straightforward way to run something on a schedule without fighting the
framework's build.

## What it does (`src/index.ts`, runs hourly — see `wrangler.jsonc`'s `triggers.crons`)

1. Inserts a `job_runs` row (`status: 'running'`).
2. Collects recent news (`collectRecentNews`, `src/domain/news-collection.ts`
   in the main app — reused here directly, since it's just a TS import,
   not a network call to the other Worker).
3. Calls TypeSafe AI's System One API once for all 16 regions with that
   evidence (`TypeSafeAiClassificationService`).
4. For each region: inserts a `region_classifications` row (full history,
   nothing overwritten), inserts one `classification_evidence` row per
   collected headline, and updates that region's live snapshot
   (`regions.current_status` / `last_classified_at` / `status_expires_at`)
   — see `src/repositories/classification-writer.ts`.
5. Marks the `job_runs` row `succeeded` (with a small summary) or
   `failed` (with the error message).

If a run fails outright (step 2 or 3 throws), existing regions are left
at their last good status rather than being forced to UNKNOWN — one
missed hourly run shouldn't blank out the whole site. `resolveEffectiveStatus`
(`src/domain/region.ts`, applied in `RegionRepository`) is the actual
safety net: a classification's `status_expires_at` (2 hours from
`classified_at`) means a couple of consecutive missed/failed runs still
age the status back to UNKNOWN on its own, without any special-casing in
the job itself.

## Deploying and running it

See `DEPLOYMENT.md` for the full steps. In short:

```bash
npm run scheduler:secret    # once: npx wrangler secret put TYPESAFE_AI_API_KEY --config scheduler/wrangler.jsonc
npm run scheduler:deploy    # npx wrangler deploy --config scheduler/wrangler.jsonc
```

It shares the same D1 database as the main app (same `database_id` in
`scheduler/wrangler.jsonc` as the root `wrangler.jsonc`) — no separate
database to create or migrate.

## Local testing

```bash
npm run scheduler:trigger   # wrangler dev --config scheduler/wrangler.jsonc --test-scheduled
```

This starts a local dev session for the scheduler Worker and lets you
fire the `scheduled()` handler on demand (via the printed
`/__scheduled` endpoint) against your local D1 — useful for testing a
run without waiting for the top of the hour.

## What's still not built

- News collection is a fixed set of RSS search queries shared across all
  16 regions (see `src/domain/news-collection.ts`'s doc comment) — not
  regional-outlet-specific or scored per region.
- No retry/backoff beyond "the next hourly run tries again."
- No alerting on repeated `job_runs` failures.
